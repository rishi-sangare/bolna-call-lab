Bolna voice agent: calls drop at 12 seconds

This page covers the research, the root-cause analysis and the prototype plan for the Upwork invite. The goal is to reproduce the 12-second disconnect inside real Bolna code, diagnose it automatically, fix it, and show a stable, low-latency call, all before the client gives us access to anything.

01Summary in 60 seconds

Plain English

Bolna runs a small "is anyone still talking?" check every 2 seconds. If neither the AI nor the caller has spoken for 10 seconds, it hangs up. 10 seconds plus up to 2 seconds before the next check is the 12 seconds the client sees.

On a healthy call that never happens, because the agent greets the caller and the caller answers. So a clean 12-second drop means something in the pipeline is silently broken. Either the caller never hears the agent (a text-to-speech or audio-format problem), or the agent never "hears" the caller (a speech-to-text or encoding problem). Bolna can't tell the difference from real silence, so it ends the call as inactivity_timeout.

Our pitch: "I reproduced your exact bug inside Bolna's own code, built a tool that names the cause from the call logs, and here's the fixed call running for 2 minutes."

  1. Run real Bolna locally (open-source, Docker: the Bolna app plus Redis). It's the same engine the hosted platform is built on.
  2. Call it with a fake Twilio: a Python client that speaks Twilio's exact Media Streams protocol, streaming a scripted caller voice (WAV) and playing the agent's replies. No phone carrier, no trial-account blocks, and the same result on every take.
  3. Flip one setting at a time to reproduce each root cause. Each one drops at about 12 s.
  4. Call Doctor reads Bolna's logs and the caller's event log and draws a timeline. It shows who hung up and why, flags which event is missing, and names the cause.
  5. Apply the fix and show a 2-minute call with interruptions and a per-turn latency breakdown.

04Why exactly 12 seconds

From the source code C
  • task_manager.py: hang_conversation_after = conversation_config.get("hangup_after_silence", 10), and __check_for_completion() loops with await asyncio.sleep(2).
  • The "user last spoke" time is reset only by a transcript. The "AI last spoke" time is reset by Twilio's mark acknowledgement, which arrives after the audio has actually played.
  • The hangup check runs before the "are you still there?" check. With both set to 10 s, the reminder never plays.
  • Other hard-coded timeouts: __await_stream_sid(timeout=10), Deepgram connect timeout 10 s, hangup_mark_event_timeout=10.

A, B and C are the top suspects for a clean ~12 s drop. Infrastructure idle timeouts (load balancer 60 s, Cloudflare 100 s, ngrok) work on a different time scale and are unlikely here.

0630-minute diagnosis playbook

  1. (3 min) Get the IDs. One failing call: CallSid, Bolna execution_id, the Deepgram request ID, and UTC times of answer and hangup.
  2. (5 min) Who hung up? Bolna's hangup_by / hangup_code / hangup_reason, and Twilio's "Who hung up", Debugger alerts (31920/31921/31924/11200) and any answering-machine detection result. The reason code often names the culprit outright.
  3. (5 min) Config review. hangup_after_silence, call_terminate, transcriber encoding/sampling_rate, synthesizer format and voice, voicemail, the LLM hangup prompt, the online check.
  4. (7 min) Line up the logs. In order: websocket accepted → start → first media → STT connected → first interim transcript → TTS first chunk → first mark ack → hangup line. The first missing event is the broken component.
  5. (5 min) Test by elimination. Set hangup_after_silence to 60. If the drop moves, the silence watchdog is confirmed, and the task becomes finding why nothing is flowing. Swap the TTS or STT provider to isolate the faulty component.
  6. (5 min) Platform checks. Twilio trial status, container restarts or out-of-memory kills, worker count, the ngrok inspector.

09The fake Twilio caller

  • Sends exactly what Twilio sends: connected, then start with streamSid, callSid, mediaFormat {audio/x-mulaw, 8000, 1} and customParameters, then 160-byte, 20 ms media frames, then stop.
  • Plays the agent's media through the speakers live, so it's audible in the video. Echoes mark events back in playback order, as Twilio does, and honours clear (interruption).
  • Scripted caller: lines come from a caller script, rendered once to mulaw WAV with a TTS voice and cached, then played with realistic pauses. Every take is identical.
  • Writes events.jsonl with wall-clock timestamps, plus call.wav (stereo: caller left, agent right) for the video.
  • Optional --mic mode: talk to the agent live.

10Call Doctor

  • Inputs: the caller's events.jsonl, Bolna container logs (parsed by pattern), and adapters for the client's data: GET /executions/{id}, /executions/{id}/log, Twilio Call Events and Voice Insights "Who hung up".
  • Timeline UI: swim lanes for Caller, Telephony, STT, LLM, TTS and Watchdog. Events plotted against call time, with the 10 s silence window shaded and the hangup marked.
  • Missing-event detector: walks the expected chain (start → media → STT connect → interim transcript → TTS first byte → mark ack). The first gap is highlighted.
  • Rules engine: for example "inactivity_timeout + no user transcript + transcriber encoding ≠ stream encoding → encoding mismatch (confidence high)".
  • Output: a one-paragraph diagnosis with the fix (as a config diff), as HTML and as text to paste into an Upwork message.

16Proposal (draft)

Hi! A drop at about 12 seconds in Bolna is almost always its 10-second silence watchdog (it checks every 2 s, so it fires between 10 and 12 s). It fires because the agent's audio or the caller's transcripts are silently not flowing, most often a transcriber encoding mismatch (linear16/16k vs Twilio's mulaw/8k) or a TTS/output-format failure.

I reproduced this inside Bolna's own open-source engine, built a small "Call Doctor" that names the cause from the call logs, and recorded the fix: [Loom link]

To pin down yours quickly:
1. Hosted Bolna or self-hosted? Twilio, Plivo or Exotel, and is the Twilio account on trial?
2. One or two execution IDs, plus the hangup_by / hangup_reason they show
3. Does every call drop, inbound and outbound? Does the greeting play, and does the agent ever reply?
4. Which transcriber and voice are configured, and are voicemail detection or prompt-based hangup on?

Given one execution ID I can usually name the cause within an hour, then tune latency and conversation flow for production.

Rate: the client posted $5–50/hr and wants an expert. Bid $40–45/hr. Optionally offer a fixed first milestone, "root cause + fix", so the client takes no risk on the first deliverable.
